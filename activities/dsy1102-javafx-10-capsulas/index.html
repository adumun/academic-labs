JavaFX en 10 cápsulas:
de una ventana a una app que recuerda

Construye por incrementos una pequeña colección de videojuegos. Cada etapa agrega una capacidad comprobable: interfaz, eventos, tabla, navegación, separación de responsabilidades y persistencia. El código lo escribes y ejecutas en IntelliJ; esta página te acompaña, no te entrega el programa resuelto.

Tu avance en la ruta0 de 10 cápsulas completadas

Tu misión: una colección personal de videojuegos

Una persona quiere registrar los juegos que tiene, consultar su colección en una tabla y conservar los datos cuando cierre la aplicación. Cada registro tendrá código único, título, plataforma y año de lanzamiento.

La aplicación comenzará sencilla y crecerá contigo. No necesitas agregar funciones que no se solicitan: el desafío consiste en conectar correctamente las piezas que ya conoces.

Antes de comenzar

  • IntelliJ IDEA y JDK 21 instalados.
  • Acceso a Maven para descargar las dependencias.
  • Un proyecto JavaFX/Maven que puedas ejecutar.
  • Ten a mano las guías y ejemplos de las semanas 09, 10 y 11.

Regla de avance: intenta resolver, abre la pista si te atascas y comprueba el resultado antes de marcar el checkpoint.

01

Primero, que la ventana abra

Proyecto Maven, configuración JavaFX y ciclo de vida

08 min

Contexto

La colección necesita una aplicación de escritorio. Antes de diseñar pantallas o registrar juegos, debes tener una base que compile y abra una ventana JavaFX.

Objetivo

Crear y ejecutar un proyecto Maven con Java 21 y JavaFX, identificando dónde comienza la aplicación y cómo aparece la ventana.

Qué debes hacer

  • Crea un proyecto nuevo llamado ColeccionVideojuegosFX usando Java 21 y Maven.
  • Comprueba que las dependencias y la configuración de JavaFX sean compatibles con el JDK.
  • Ejecuta la aplicación y cambia el título de la ventana por «Mi colección de videojuegos».

Respuesta esperada

Una ventana JavaFX se abre sin errores de compilación ni de arranque. Puedes señalar qué clase inicia la aplicación y distinguir el trabajo de Maven del ciclo de vida JavaFX.

Necesito una pista para avanzar

Si la ventana no aparece, no cambies varias cosas a la vez. Revisa primero la versión del JDK, el nivel de compilación configurado en Maven y las dependencias JavaFX; después fuerza la recarga del proyecto Maven y vuelve a ejecutar. Ubica también el método de entrada de la aplicación y el punto donde se prepara la ventana: separar configuración, arranque y presentación te ayudará a diagnosticar sin adivinar.

Checkpoint de la cápsula

02

Diseña la pantalla antes de programar su comportamiento

Scene Builder, FXML y Controller

10 min

Contexto

La persona necesita un formulario para ingresar los datos de cada videojuego. La distribución visual debe poder modificarse sin mezclarla con las reglas del programa.

Objetivo

Construir una vista FXML con Scene Builder y vincularla a un Controller, reconociendo la función de los identificadores de controles.

Qué debes hacer

  • Crea una vista inicial con un título, campos para código y título, una selección de plataforma, un campo para año y un botón de registro.
  • Agrega un espacio para mostrar mensajes al usuario.
  • Guarda el FXML dentro de los recursos del proyecto y vincúlalo con su Controller.
  • Abre la vista desde la aplicación y comprueba que se renderiza.

Respuesta esperada

La ventana muestra todos los controles en una distribución legible. El FXML carga sin excepciones y queda asociado al Controller previsto, aunque el botón todavía no realice el registro.

Necesito una pista para avanzar

Piensa en FXML como la descripción de la interfaz y en Scene Builder como una herramienta para editar esa descripción visualmente. Cada control que necesites consultar desde Java debe tener una identidad coherente; la vista también debe declarar qué Controller la atiende. Si FXMLLoader falla, revisa la ruta del recurso, el nombre del controlador y la estructura XML antes de reconstruir el proyecto.

Checkpoint de la cápsula

03

Haz que los controles reaccionen

Campos, anotaciones @FXML y eventos

10 min

Contexto

La pantalla ya existe, pero el botón no hace nada. El usuario necesita una respuesta visible cuando interactúa con el formulario.

Objetivo

Conectar controles FXML con atributos del Controller y responder a un evento sin introducir todavía persistencia ni reglas complejas.

Qué debes hacer

  • Vincula en el Controller los campos que necesitas leer y el espacio donde mostrar mensajes.
  • Asocia el botón a un método manejador de evento.
  • Al pulsarlo, lee los valores ingresados y muestra una confirmación que permita reconocer qué información recibió la aplicación.
  • Prueba el botón con campos completos y vacíos.

Respuesta esperada

El clic ejecuta el método esperado y la interfaz muestra una respuesta coherente con los valores ingresados. No hay errores de controles sin vincular ni referencias nulas.

Necesito una pista para avanzar

El Controller actúa como puente entre la vista y el comportamiento. Comprueba que los identificadores declarados en FXML coincidan con los atributos que Java intenta inyectar y que el nombre del manejador coincida con el evento configurado. Primero consigue una reacción pequeña y observable; deja las reglas de negocio para una capa posterior, en vez de convertir el método del botón en el lugar donde ocurre todo.

Checkpoint de la cápsula

04

Que la interfaz también se entienda a simple vista

CSS aplicado a JavaFX

08 min

Contexto

La aplicación funciona, pero los controles se ven desordenados y no hay jerarquía visual. Una interfaz clara reduce errores al ingresar información.

Objetivo

Aplicar una hoja CSS a la escena y utilizar clases de estilo para mejorar la presentación sin cambiar la lógica Java.

Qué debes hacer

  • Crea una hoja CSS dentro de los recursos del proyecto.
  • Define estilos para el fondo, títulos, campos, botón principal y mensajes.
  • Asigna clases de estilo a los controles que correspondan.
  • Comprueba que el diseño siga siendo legible al cambiar el tamaño de la ventana.

Respuesta esperada

La aplicación carga su CSS sin errores y presenta una jerarquía visual consistente. Los eventos de la cápsula anterior siguen funcionando exactamente igual.

Necesito una pista para avanzar

JavaFX no utiliza exactamente el mismo conjunto de selectores que una página web, aunque la idea de CSS sea familiar. Asegúrate de que la hoja esté realmente asociada a la escena o al nodo raíz y que las clases que escribes existan en los controles. Si un estilo no aparece, revisa primero la ruta del archivo y el nombre de la clase; no intentes corregirlo agregando estilos en muchos lugares distintos.

Checkpoint de la cápsula

05

Del formulario a una colección visible

Modelo Java, TableView y ObservableList

12 min

Contexto

Mostrar un mensaje de confirmación no basta: el usuario necesita consultar los videojuegos registrados y distinguir cada dato en una tabla.

Objetivo

Representar un videojuego como objeto Java y mostrar una colección mediante TableView conectada a ObservableList.

Qué debes hacer

  • Crea el modelo Videojuego con código, título, plataforma y año.
  • Agrega una TableView con una columna por dato relevante.
  • Prepara una ObservableList con dos videojuegos de prueba y conecta la tabla a esa lista.
  • Haz que el registro de prueba agregue un objeto a la lista y observa la tabla.

Respuesta esperada

La tabla presenta correctamente los dos registros de prueba. Al agregar otro videojuego a la ObservableList aparece una nueva fila sin tener que reconstruir toda la ventana.

Necesito una pista para avanzar

Separa tres ideas: el modelo representa un videojuego, la lista mantiene varios objetos y la tabla los presenta. ObservableList es útil porque comunica cambios a los controles JavaFX que la observan; una lista común no ofrece por sí sola esa notificación. Revisa también cómo cada columna obtiene el valor del atributo correspondiente y confirma que el tipo declarado en la columna sea compatible.

Checkpoint de la cápsula

06

Dos pantallas, la misma colección

Navegación FXML y estado compartido

12 min

Contexto

El formulario y el listado ya tienen responsabilidades visuales distintas. La aplicación necesita navegar entre ambos sin perder los videojuegos ingresados.

Objetivo

Separar el listado y el formulario en dos vistas FXML y navegar entre ellas conservando una única fuente de estado en memoria.

Qué debes hacer

  • Organiza una vista FXML para el listado y otra para el formulario.
  • Implementa la navegación con FXMLLoader y la misma ventana principal.
  • Comparte la colección o el objeto responsable de los datos entre los controladores.
  • Registra un videojuego, vuelve al listado y repite la navegación para comprobar que no se pierde.

Respuesta esperada

La navegación listado → formulario → listado funciona varias veces en la misma ventana. El nuevo videojuego continúa visible al regresar y no aparecen colecciones duplicadas o reiniciadas.

Necesito una pista para avanzar

FXMLLoader crea una vista y su Controller; cargar otra vista no significa que debas crear otra colección de datos. Piensa dónde debe vivir el estado que ambas pantallas necesitan y cómo reciben acceso a esa misma instancia. Si al volver desaparecen las filas, revisa si estás creando una lista nueva al abrir cada pantalla o si cada Controller trabaja con una referencia diferente.

Checkpoint de la cápsula

07

El Controller no tiene que saberlo todo

MVC, Service y reglas de validación

14 min

Contexto

Ahora el método del botón empieza a concentrar lectura de campos, validaciones y registro. Cada nueva regla vuelve más difícil mantener el Controller.

Objetivo

Separar responsabilidades y trasladar las reglas de registro a un Service, manteniendo al Controller como coordinador de la interacción.

Qué debes hacer

  • Identifica qué pertenece al modelo, qué corresponde a la vista y qué coordina el Controller.
  • Crea un Service que reciba los datos del videojuego y aplique las reglas de registro.
  • Rechaza código o título vacío, año inválido y código repetido.
  • Haz que el Controller invoque al Service y presente el resultado o el error al usuario.

Respuesta esperada

Un registro válido se incorpora a la colección. Un dato inválido o un código duplicado se rechaza sin alterar los registros existentes. El Controller ya no contiene las reglas de negocio ni manipula archivos.

Necesito una pista para avanzar

Una buena separación se reconoce por las preguntas que puede responder cada clase. El modelo describe el videojuego; el Service decide si se puede registrar y coordina la operación; el Controller traduce la interacción del usuario en una llamada y muestra su resultado. Si el Controller conoce demasiados detalles, pregúntate qué responsabilidad podría moverse sin que la vista necesite saber cómo está implementada.

Checkpoint de la cápsula

08

Guardar datos sin llenar el Controller de JSON

DAO, Jackson y serialización

16 min

Contexto

La colección vive en memoria. Si el programa termina, los videojuegos desaparecen. Necesitas almacenar los objetos en un archivo, pero la interfaz no debería conocer el formato ni la ruta.

Objetivo

Definir un contrato DAO y una implementación JSON con Jackson para convertir objetos Java a JSON y recuperar objetos desde ese archivo.

Qué debes hacer

  • Define operaciones de lectura y escritura para la colección, sin acoplar el contrato a Jackson.
  • Implementa el DAO JSON utilizando Jackson y un archivo data/videojuegos.json.
  • Conecta el Service con el DAO para cargar y guardar los datos.
  • Registra dos videojuegos y revisa el contenido generado en el archivo.

Respuesta esperada

El archivo contiene una representación JSON legible de los videojuegos. La lectura reconstruye objetos Java equivalentes y el Controller no importa Jackson ni conoce la ruta del archivo.

Necesito una pista para avanzar

Serializar significa transformar objetos en una representación que pueda almacenarse; deserializar realiza el recorrido inverso. El DAO concentra el acceso al archivo y la biblioteca de mapeo, mientras que el Service decide cuándo corresponde leer o guardar. Comprueba el resultado en ambos sentidos: no basta con que el archivo se cree; también debes poder recuperar una colección equivalente a partir de él.

Checkpoint de la cápsula

09

Cerrar y abrir no debería borrar tu colección

Carga inicial, persistencia y errores de archivo

14 min

Contexto

El archivo JSON ya existe, pero todavía debes demostrar que la aplicación lo utiliza al iniciar y que distingue una colección vacía de un problema de lectura.

Objetivo

Integrar la carga inicial y verificar la persistencia real entre ejecuciones, con tratamiento visible de los errores de entrada/salida.

Qué debes hacer

  • Haz que la aplicación cargue los registros desde el DAO al iniciar.
  • Registra al menos dos videojuegos, cierra completamente la aplicación y vuelve a ejecutarla.
  • Comprueba el comportamiento cuando el archivo todavía no existe.
  • Provoca o simula un error de lectura y evita que se presente como si la colección estuviera vacía sin explicación.

Respuesta esperada

Después de reiniciar, la tabla vuelve a mostrar los registros almacenados. Si el archivo no existe, la aplicación puede comenzar con una colección vacía; si existe pero no puede leerse, el problema se informa y no se oculta como una carga exitosa.

Necesito una pista para avanzar

La tabla, la colección en memoria y el archivo son estados distintos. Para demostrar persistencia, cierra el proceso completo: refrescar la pantalla no prueba que el DAO haya escrito ni que la aplicación haya leído al arrancar. Trata por separado el caso de archivo inexistente y el de archivo ilegible; convertir cualquier excepción en una lista vacía puede ocultar una pérdida de información.

Checkpoint de la cápsula

10

Un archivo dañado no se arregla fingiendo que no pasó nada

JSON estricto, resguardo y pruebas

16 min

Contexto

Un archivo puede quedar mal formado o contener claves repetidas. Si la aplicación lo sobrescribe silenciosamente, puede destruir información que todavía era recuperable.

Objetivo

Reconocer fallos de integridad JSON, conservar evidencia del archivo problemático y verificar el comportamiento del DAO mediante pruebas.

Qué debes hacer

  • Prueba un JSON mal formado y otro que repita una clave dentro del mismo objeto.
  • Verifica que la lectura estricta rechace el contenido ambiguo o inválido.
  • Comprueba que el archivo original no se sobrescriba silenciosamente y que se conserve una copia diagnóstica cuando corresponda.
  • Revisa la función del respaldo .bak: conserva una versión previa, pero no presupongas que la aplicación la restaura automáticamente.
  • Ejecuta las pruebas disponibles y registra qué comportamiento comprueba cada una.

Respuesta esperada

El contenido mal formado o con claves duplicadas se rechaza; la aplicación informa el problema, conserva el archivo para diagnóstico y evita guardar encima de datos que no pudo validar. Puedes explicar qué protege el archivo .bak, qué hace la copia .corrupt y qué demuestran las pruebas ejecutadas.

Necesito una pista para avanzar

No todos los errores JSON son iguales: una coma incorrecta rompe la sintaxis, mientras que una clave duplicada puede ser aceptada por algunos lectores y producir ambigüedad. Por eso conviene configurar una lectura estricta y probar ambos casos. Antes de guardar, piensa qué versión del archivo estás reemplazando y qué evidencia deberías conservar si la lectura falla. Un respaldo no equivale a una restauración automática: documenta y verifica exactamente lo que tu implementación hace, sin atribuirle capacidades que no tiene.

Checkpoint de la cápsula

Cierre de la misión

Antes de terminar, comprueba que puedes explicar el recorrido completo de los datos, no solo mostrar una ventana funcionando.

  • La vista FXML recibe eventos y el Controller coordina la interacción.
  • El modelo representa videojuegos; la tabla observa una colección.
  • El Service aplica reglas y el DAO se ocupa de la persistencia JSON.
  • El reinicio demuestra la lectura desde disco; las pruebas de error demuestran qué ocurre cuando los datos no son confiables.
