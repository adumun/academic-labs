Kafka Game Day

Cuando un evento falla, el sistema debe decidir si reintenta, rechaza o deriva el mensaje. Investiga el comportamiento de una arquitectura basada en Kafka y defiende una política de recuperación con evidencia real.

DSY1107100–120 minutosWindows + Docker DesktopSpring Boot · Kafka · JMeter
Abrir guía completa ↗ Volver al catálogo
Tu misión

Investiga los fallos, no solo el código HTTP

Una tienda publica compras como eventos. Algunos se procesan normalmente, otros fallan temporalmente y otros contienen errores que no se resolverán reintentando. Tu equipo debe seguir el recorrido del mensaje y explicar qué ocurre con cada caso.

Al terminar podrás:

  • Distinguir un fallo transitorio de un error permanente de contrato.
  • Observar reintentos y explicar cuándo un mensaje termina en una Dead Letter Topic (DLT).
  • Relacionar topic, partición, offset y consumer lag.
  • Explicar por qué HTTP 201 confirma la publicación, pero no el procesamiento final.
  • Proponer una política de recuperación y sus límites.
Antes de comenzar

Requisitos

  • Windows 10/11 y PowerShell.
  • Docker Desktop iniciado.
  • Docker Compose V2.
  • Internet para la primera descarga/compilación.
  • Puertos 8081, 8082, 8083, 5173 y 9092 disponibles.

No necesitas instalar Java, Maven, Node ni JMeter si utilizas el runner Docker. Para abrir JMeter GUI necesitas Java 17 o superior.

Prueba de carga

2. Ejecutar JMeter sin instalarlo en Windows

Con el stack iniciado, ejecuta el mismo plan JMeter desde Docker. Este ejemplo genera una línea base pequeña de 5 usuarios por 5 vueltas.

POWERSHELL · DESDE kafka-resilience-game-dayRunner Docker
Push-Location ..\kafka-compras-webapp

docker compose --env-file ..\kafka-resilience-game-day\.env.game-day -f compose.yaml -f ..\kafka-resilience-game-day\compose.game-day.yaml --profile app --profile pipeline --profile load run --build --rm jmeter-runner -t /tests/carga-compras.jmx -Jhost=compras-api -Jport=8080 -Jthreads=5 -Jloops=5 -JclientePrefix=LAB-OK- -l /results/baseline.jtl

Pop-Location

Falla transitoria

Usa el prefijo SIM-RETRY- para observar los intentos y la recuperación del mensaje.

Falla persistente

Usa SIM-DLT- para seguir el evento hasta compras-dlt y revisar sus headers.

Evidencias

3. Registra lo que realmente observaste

Conserva las capturas de Kafka UI, los resultados JMeter y los logs. Completa el DevLog con los checkpoints E0–E4, las respuestas y una política de recuperación justificada.

No inventes tasas, offsets ni resultados. Espera a que el consumidor termine de procesar antes de comparar conteos.

Apagado seguro

4. Cierra después de guardar

POWERSHELL · DESDE LA CARPETA DEL LAB
