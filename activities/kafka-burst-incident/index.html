Operación Avalancha

Cinco minutos de tráfico creciente, un sistema distribuido bajo presión y una pregunta: ¿qué componente se atrasa primero? Diagnostica con métricas, formula una hipótesis y demuestra si tu mejora realmente funciona.

DSY1107100–120 minutosWindows + Docker DesktopKafka · JMeter · Consumer lag
Abrir guía completa ↗ Volver al catálogo
Tu misión

Encuentra el cuello de botella con evidencia

La API sigue recibiendo compras, pero eso no significa que todos los consumidores estén al día. Debes distinguir publicación HTTP, procesamiento Kafka y evolución del backlog. No se entrega una solución prefabricada: tu equipo investiga, interviene y compara dos corridas equivalentes.

Al terminar podrás:

  • Interpretar throughput, latencia y consumer lag durante una carga escalonada.
  • Distinguir un evento publicado de uno procesado por el consumidor.
  • Formular y contrastar hipótesis con evidencia de JMeter, Kafka UI y logs.
  • Proponer una mejora y explicar sus costos, límites y riesgos.
  • Comparar mediciones ANTES/DESPUÉS sin cambiar el perfil de carga.
Antes de comenzar

Requisitos

  • Windows 10/11 y PowerShell.
  • Docker Desktop iniciado.
  • Docker Compose V2.
  • Internet para la primera descarga/compilación.
  • Puertos 8081, 8082, 8083, 5173 y 9092 disponibles.

No necesitas instalar Maven, Node, Java ni JMeter localmente: el script ejecuta JMeter mediante Docker. JMeter GUI es opcional.

Inicio rápido

1. Obtener y levantar el laboratorio

Abre Docker Desktop. Si todavía no tienes el repositorio, clónalo y entra a la carpeta del laboratorio:

POWERSHELL · CLONACIÓN INICIALWindows
git clone https://github.com/cmartinezs/DSY1107-DESARROLLO-CLOUD-NATIVE-I-2026-2.git
cd DSY1107-DESARROLLO-CLOUD-NATIVE-I-2026-2\labs\kafka-burst-incident

Si ya tienes una copia, actualízala desde la raíz del repositorio y luego entra a la carpeta:

POWERSHELL · ACTUALIZARDesde la raíz del repo
git switch master
git pull --ff-only origin master
cd labs\kafka-burst-incident
POWERSHELL · INICIARDesde kafka-burst-incident
.\scripts\iniciar.ps1
API de salud ↗ Kafka UI ↗

En Kafka UI revisa los topics compras, compras-validas y compras-rechazadas, y localiza el consumer group procesador-s13. No continúes si el stack no está saludable.

Corrida ANTES

2. Medir la oleada de 300 segundos

Abre dos terminales PowerShell en labs\kafka-burst-incident. Inicia primero el monitor en la segunda terminal; después ejecuta la oleada en la primera.

Terminal 2 · Monitor

Captura el consumer lag antes, durante y después de la oleada.

POWERSHELL
.\scripts\monitorear-lag.ps1 -RunId antes -Snapshots 35 -EverySeconds 10

Terminal 1 · JMeter

Ejecuta el perfil completo de cinco minutos.

POWERSHELL
.\scripts\ejecutar-oleada.ps1 -RunId antes
POWERSHELL · RESUMIR LA CORRIDACuando terminen ambas terminales
.\scripts\resumir-jmeter.ps1 -RunId antes

Se guardan results\oleada-antes.jtl, results\lag-antes.txt y results\resumen-antes.csv. El monitor tarda aproximadamente 5 min 40 s para incluir la recuperación posterior a la carga.

Calibrar la intensidad

3. Si tu equipo tiene recursos limitados

Puedes reducir las tasas objetivo a la mitad sin cambiar la duración de 300 segundos ni el número máximo de usuarios configurados:

POWERSHELL · CARGA REDUCIDA
.\scripts\ejecutar-oleada.ps1 -RunId antes -LoadScale 0.5

Anota el factor utilizado. Para una comparación válida, usa el mismo factor en las corridas ANTES y DESPUÉS.

Corrida DESPUÉS

4. Intervenir y comparar

Guarda primero la línea base. Conserva JTL, snapshots de lag, resumen, capturas y observaciones.

Detén el stack. Ejecuta el script de apagado después de guardar la evidencia.

Aplica una mejora razonada en tu copia del código o configuración. Explica qué indicador debería cambiar y qué costo introduces.

Levanta nuevamente y repite exactamente el mismo perfil de carga, usando el identificador despues.

POWERSHELL · DETENER Y REINICIAR
.\scripts\detener.ps1
# Aplica tu cambio razonado al código o configuración.
.\scripts\iniciar.ps1

Terminal 2 · Monitor

POWERSHELL
.\scripts\monitorear-lag.ps1 -RunId despues -Snapshots 35 -EverySeconds 10

Terminal 1 · JMeter

POWERSHELL
.\scripts\ejecutar-oleada.ps1 -RunId despues
POWERSHELL · RESUMIR DESPUÉS
.\scripts\resumir-jmeter.ps1 -RunId despues

Compara tasa HTTP realmente lograda, errores, latencia, lag máximo y tiempo de recuperación. No declares una mejora a partir de una única captura.

Entrega

5. Construye tu diagnóstico

Documenta en tu DevLog la hipótesis, evidencia ANTES/DESPUÉS, modificación aplicada, contrapartidas y límites. Distingue siempre valores objetivo del generador y valores observados.

La guía completa contiene preguntas de diagnóstico, tabla comparativa y criterios de defensa técnica.

Apagado seguro

Antes de cerrar

POWERSHELL · DESDE LA CARPETA DEL LAB
.\scripts\detener.ps1

El broker local no tiene volumen persistente. Al detener el stack se eliminan mensajes y offsets; guarda primero toda tu evidencia.
